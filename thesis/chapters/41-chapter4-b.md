## 4.4 Реалізація автентифікації та авторизації

**4.4.1 Конфігурація Auth.js.** Автентифікацію реалізовано у файлі `lib/auth/auth.ts` вебзастосунку трьома провайдерами Auth.js. Провайдер Google (ФВ-01) передає параметр `prompt: 'select_account'`, тож вибір облікового запису пропонується під час кожного входу [@authjs-google]. Два провайдери типу Credentials, у яких рішення ухвалює власна функція `authorize` [@authjs-credentials], обслуговують гостьовий сеанс (`guest`, ФВ-03) і завершення входу з настільного застосунку (`desktop`, ФВ-02). Параметри сеансу наведено в лістингу @lst:authjs.

```{#lst:authjs .ts caption="Стратегія сеансу та параметри файлу cookie в конфігурації Auth.js"}
const config: NextAuthConfig = {
  adapter,
  session: {
    strategy: 'jwt',
  },
  useSecureCookies: useSecureAuthCookies,
  cookies: {
    sessionToken: {
      name: SESSION_COOKIE_NAME,
      options: {
        httpOnly: true,

        sameSite: 'lax',
        path: '/',
        secure: useSecureAuthCookies,
      },
    },
  },
  providers: [
    // ...
  ],
```

Сеанс зберігається в зашифрованому токені у файлі cookie [@authjs-session-strategies]. Атрибут HttpOnly закриває cookie від сценаріїв сторінки, SameSite=Lax обмежує його надсилання з інших сайтів, а Secure дозволяє передавання лише через HTTPS [@mdn-set-cookie]. Ознака `useSecureAuthCookies` спільного пакета `shared` істинна лише у виробничому середовищі, і тоді ім'я cookie отримує префікс `__Secure-`, з яким браузер приймає його тільки від захищеної сторінки [@mdn-set-cookie]. Функції зворотного виклику `jwt` і `session` переносять у токен і сеанс роль користувача. Гостьовий провайдер створює запис із роллю `guest` і випадковим іменем, ідентифікатор якого сторінка перегляду зберігає в `localStorage` для повторного використання.

**4.4.2 Обмеження доступу.** Файл `proxy.ts` (ФВ-04) [@nextjs-proxy] не вважає гостьовий сеанс входом і перенаправляє такого відвідувача на `/login` з усіх сторінок, крім головної, сторінки входу та `/desktop-auth`. Шаблон `matcher` виключає з перевірки API-маршрути, статичні файли й шляхи `<UUID>/watch`, тому перегляд доступний без облікового запису Google.

Сервер сигналізації самостійно розшифровує той самий cookie (лістинг @lst:jwt-verify). Ключ розшифрування `@auth/core` виводить із секрету та «солі» – імені cookie, тому сервер бере це ім'я зі спільного модуля, а `AUTH_SECRET` обох сервісів збігаються.

```{#lst:jwt-verify .ts caption="Перевірка сеансового cookie на сервері сигналізації"}
export const NEXT_AUTH_SALT = SESSION_COOKIE_NAME;

export async function decodeAuthToken(rawToken: string): Promise<JWT | null> {
  const payload = await decode({
    salt: NEXT_AUTH_SALT,
    secret: env.AUTH_SECRET,
    token: rawToken,
  });

  if (!payload?.sub) return null;
  return payload;
}
// ...
export const validateWsJwt = async (
  req: FastifyRequest, reply: FastifyReply): Promise<void> => {
  const rawToken = req.cookies[NEXT_AUTH_SALT];
  // ...
  const payload = await decodeAuthToken(rawToken);

  if (!payload) {
    reply.code(401).send({ error: 'Invalid token' });
    return;
  }

  req.context.userId = payload.sub;
};
```

Функція `validateWsJwt` є хуком `preValidation` групи маршрутів `/streams` і обох маршрутів WebSocket; відповідь 401 з хука зупиняє обробку запиту [@fastify-hooks]. Належність трансляції перевіряє лише маршрут завантаження мініатюри (відповідь 403), а сокет публікації покладається на непередбачуваність UUID трансляції. Приватну трансляцію (ФВ-11) обробник `/streams/search` виключає з переліку примусовим фільтром `isPrivate = false`, а переглянути її може кожен, хто має посилання.

**4.4.3 Вхід у настільному застосунку.** Послідовність входу наведено на рис. @fig:seq-desktop-auth, а її початок у головному процесі Electron – у лістингу @lst:pkce.

```{#lst:pkce .ts caption="Параметри PKCE і запуск входу в системному браузері"}
  const verifier = base64url(randomBytes(32));
  const challenge = createHash('sha256').update(verifier).digest('base64url');
  const state = base64url(randomBytes(16));
  // ...
        const port = await listen(server);
        // ...
        const url = new URL('/api/desktop-auth/start', __WEB_URL__);
        url.searchParams.set('port', String(port));
        url.searchParams.set('state', state);
        url.searchParams.set('challenge', challenge);

        await shell.openExternal(url.toString());
```

Локальний сервер слухає `127.0.0.1` на порту, призначеному операційною системою [@rfc8252], і відхиляє запити з чужим `state`. Вебзастосунок (`lib/auth/desktopHandoff.ts`) перевіряє параметри схемою zod, адресу повернення будує з фіксованого `http://127.0.0.1:<port>/callback`, що виключає відкрите перенаправлення, а запит і одноразовий код шифруються з різними «солями», тож один тип токена не можна підставити замість іншого. Провайдер `desktop` порівнює SHA-256 від `verifier` з `challenge` коду функцією сталого часу `timingSafeEqual` [@rfc7636] і відхиляє повторний `jti`. Реєстр `jti` зберігається в пам'яті процесу, тому за кількох екземплярів вебзастосунку одноразовість не гарантована.

Вхід за паролем, обмеження спроб входу та журнал аудиту не реалізовано: стовпці `password_hash`, `failed_login_count`, `locked_until` і таблиця `audit_log` лише зарезервовані у схемі. Сеанс JWT неможливо відкликати до завершення строку дії [@authjs-session-strategies].

## 4.5 Реалізація рівня даних і програмного інтерфейсу сервера

**4.5.1 Пакет бази даних.** Таблиці (рис. @fig:er) описано функцією `pgTable` у пакеті `db`, а зв'язок трансляції зі стрімером і глядачами – функцією `defineRelations`. Типи рядків виводяться зі схем (`$inferSelect`, `$inferInsert`), тому вебзастосунок і сервер сигналізації використовують одні типи без генерації коду [@drizzle-overview]. Файлів міграцій немає: контейнер `migrate` виконує `drizzle-kit push --force`, що застосовує відмінності схеми безпосередньо до бази даних [@drizzle-kit-push]. Вебзастосунок звертається до бази даних лише через власний адаптер Auth.js `DrizzleAdapter`, а об'єкт підключення створюється під час першого запиту, тому `next build` не потребує бази даних.

**4.5.2 Шари сервера сигналізації.** Репозиторії сервера інкапсулюють запити Drizzle, сервіси перетворюють відсутність запису на `EntityNotFoundError`, а контролери – помилки на коди 404, 400 чи 500 (рис. @fig:classes-signaling). Маршрути наведено в табл. @tbl:api; ззовні вони доступні через Caddy з префіксом `/sfu`.

: Маршрути програмного інтерфейсу сервера сигналізації {#tbl:api}

| Метод і шлях | Сеанс | Призначення |
|---|---|---|
| `POST /streams` | так | створення трансляції (ознака `isPrivate`) |
| `POST /streams/search` | так | сторінка публічних трансляцій з фільтрами й сортуванням |
| `GET /streams/:userId/active` | так | активна трансляція користувача |
| `GET`, `POST /streams/:streamId/thumbnail` | так (`POST` – власник) | отримання та збереження мініатюри |
| `GET /streams/:streamId` | ні | трансляція зі стрімером і глядачами |
| `GET /users/:userId` | ні | відомості про користувача |
| `GET /ws/streams/:streamId/broadcast` | так | WebSocket стрімера |
| `GET /ws/streams/:streamId/watch` | так, зокрема гостьовий | WebSocket глядача |

Метод `UsersService.registerCronJobs` реєструє в плагіні `@fastify/schedule` завдання з виразом `0 0 * * 1` (понеділок, 00:00), яке одним оператором `DELETE` видаляє гостей без активності понад 7 діб, що не дивляться жодної трансляції (ФВ-19).

**4.5.3 Перевірка конфігурації.** Функція `createEnv` пакета `env` під час запуску перевіряє змінні середовища схемою zod, вважає порожні значення відсутніми й у разі помилок виводить перелік усіх некоректних змінних та зупиняє запуск. Зокрема, `AUTH_SECRET` має містити не менше 32 символів. Секрети вебзастосунку позначено `server-only`, тож їх імпорт у клієнтський код спричиняє помилку збирання, а у виробничому середовищі `AUTH_URL` має бути адресою HTTPS, без якої cookie з атрибутом Secure не працюватиме.

## 4.6 Реалізація інтерфейсу користувача та розгортання

**4.6.1 Структура інтерфейсу.** Сторінки розміщено у двох групах маршрутів каталогу `app`: `(auth)` для `/login` і `/desktop-auth` та `(main)` зі спільними шапкою й підвалом для головної сторінки, `/broadcast`, `/[streamId]/watch`, `/privacy` і `/terms`. Серверні компоненти отримують сеанс функцією `auth()` і дані з сервера сигналізації через внутрішню мережу Docker, а клієнтські звертаються до нього через префікс `/sfu`. Головна сторінка відвідувачу показує кнопку завантаження настільного застосунку для операційної системи із заголовка `User-Agent` (ФВ-18), а користувачу – по 12 карток активних трансляцій на сторінці (ФВ-05). Базові елементи (`Button`, `Select`, `Slider` тощо) мають варіанти, описані функцією `cva` бібліотеки class-variance-authority.

**4.6.2 Теми оформлення.** Кольори задано змінними CSS для `:root` (світла тема) і класу `.dark` (темна тема), які директива `@theme` перетворює на змінні теми Tailwind CSS з класами `bg-canvas`, `text-stroke` тощо [@tailwind-theme]. Компонент `ThemeProvider` бібліотеки next-themes з параметрами `attribute="class"` і `defaultTheme="system"` обирає тему за налаштуванням операційної системи [@next-themes]; окремого перемикача теми немає. Головну сторінку в обох темах наведено на рис. @fig:scr-home-themes.

Теми різняться лише значеннями змінних кольорів, тому компонент, що використовує кольори теми, підтримує обидві без додаткового коду.

**4.6.3 Збирання та розгортання.** За теґом `v*` робочий процес GitHub Actions збирає образи `web`, `signaling` і `migrate` для розгортання (рис. @fig:deployment), а за теґом `desktop-v*` – інсталятори NSIS, DMG і AppImage засобами electron-builder [@electron-builder] для випуску GitHub. Автоматичне оновлення [@electron-builder-autoupdate] працює лише у Windows і Linux, бо в macOS воно потребує підписаного застосунку.

## Висновки до розділу 4

Систему реалізовано мовою TypeScript зі спільними пакетами протоколу, схем даних і конфігурації. Захоплення окремого застосунку з його звуком і слідування за його вікнами виконує настільний застосунок Electron, а потокову передачу – SFU mediasoup з H.264 як основним кодеком.

Автентифікація поєднує вхід через Google, гостьові сеанси та вхід настільного застосунку через системний браузер за схемою PKCE. Зашифрований сеанс JWT у cookie з атрибутами HttpOnly, SameSite=Lax і, у виробничому середовищі, Secure перевіряє й сервер сигналізації. Конфігурацію перевіряють схеми zod, а інтерфейс підтримує світлу й темну теми. Обмеженнями є відсутність перевірки власника для сокета публікації та неможливість відкликати сеанс до завершення строку дії.
