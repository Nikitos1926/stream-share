# 3 Проєктування програмної системи

## 3.1 Архітектура програмної системи

**3.1.1 Склад і розподіл відповідальності.** Програмну систему організовано як монорепозиторій pnpm [@pnpm-workspaces], у якому три виконувані модулі (`apps/*`) спираються на три спільні пакети (`packages/*`). Модулі та зв'язки між ними наведено на діаграмі компонентів (рис. @fig:components), побудованій у нотації UML [@omg-uml].

![Діаграма компонентів програмної системи](../diagrams/fig-components.png){#fig:components width=16cm}

Вебзастосунок `apps/web` (Next.js) формує сторінки, виконує автентифікацію через Auth.js і під час серверного рендерингу отримує дані про трансляції від сервера сигналізації внутрішнім HTTP-запитом. Сервер сигналізації `apps/signaling` (Fastify) надає REST-інтерфейс і WebSocket-канали [@rfc6455] для сигнальних повідомлень, а також пересилає медіапотоки як SFU на основі mediasoup [@mediasoup-design]: потік стрімера надходить на сервер один раз і розсилається кожному глядачеві без перекодування.

Настільний застосунок `apps/desktop` (Electron) не дублює інтерфейс: вікно `BrowserWindow` завантажує розгорнутий вебзастосунок, а головний процес [@electron-process-model] надає сторінці через об'єкт `window.conveyor` лише недоступне браузеру – перелік вікон з ідентифікаторами процесів, захоплення звуку застосунку в утилітарному процесі `audioWorker`, слідування за вікнами та вхід через системний браузер.

Пакет `@stream-share/db` містить схеми таблиць Drizzle ORM [@drizzle-overview], `@stream-share/shared` – типи повідомлень протоколу, ім'я cookie сеансу та розрахунок бітрейту, `@stream-share/env` – перевірку змінних середовища за схемами zod [@zod]. Тому зміна протоколу чи схеми даних перевіряється компілятором в усіх модулях. Зовнішні системи – Google OAuth 2.0 для підтвердження особи та GitHub Releases для інсталяторів і автоматичного оновлення настільного застосунку [@electron-builder-autoupdate].

**3.1.2 Розгортання.** Конфігурацію виробничого середовища задано файлом `infra/docker-compose.prod.yml` [@docker-compose-model]. Діаграму розгортання наведено на рис. @fig:deployment.

![Діаграма розгортання програмної системи](../diagrams/fig-deployment.png){#fig:deployment width=16cm}

На сервері працюють п'ять сервісів:

– `caddy` (порти 80, 443) автоматично отримує TLS-сертифікат [@caddy-https] і спрямовує запити `/sfu/*` без префікса до сервера сигналізації, а решту – до `web` (порт 3000);

– `web` (внутрішній порт 3000) запускає вебзастосунок Next.js з образу в GitHub Container Registry; змінні `AUTH_URL` (публічна адреса `https://${PUBLIC_HOST}`) і `AUTH_TRUST_HOST` налаштовують Auth.js на роботу за зворотним проксі;

– `signaling` (порт 4000) додатково публікує діапазон портів UDP і TCP `MEDIASOUP_RTC_MIN_PORT`–`MEDIASOUP_RTC_MAX_PORT`, через який медіадані йдуть до клієнтів в обхід Caddy;

– `postgres` (образ `postgres:16-alpine`) зберігає дані [@postgresql-about];

– `migrate` одноразово застосовує схему командою `drizzle-kit push`.

Мініатюри, дані СУБД і сертифікати зберігаються в томах. Доставку змін автоматизовано в GitHub Actions: тег `v*` запускає збирання образів `web`, `signaling` і `migrate` у GitHub Container Registry та їх оновлення на сервері через SSH (`docker compose pull`, `up -d`), а тег `desktop-v*` – збирання інсталяторів для Windows, macOS і Linux і їх публікацію в GitHub Release.

## 3.2 Проєктування процесів у системі

**3.2.1 Протокол сигналізації.** Клієнти та сервер обмінюються JSON-повідомленнями типів `req` (запит з `method`, `params` і `requestId`), `res` (відповідь з тим самим `requestId`, що містить `result` або помилку `{code, msg}`) та `event` (подія сервера). Методи й події з пакета `@stream-share/shared` наведено в табл. @tbl:ws-protocol; оголошений метод `setPreferredLayer` не обробляє ні сервер, ні клієнт, тому до таблиці він не увійшов.

: Методи та події протоколу сигналізації {#tbl:ws-protocol}

| Метод / подія | Канал | Напрям | Параметри → результат |
|---|---|---|---|
| `getRtpCapabilities` | broadcast | клієнт → сервер | – → можливості RTP маршрутизатора |
| `createTransport` | обидва | клієнт → сервер | `direction` (`send` / `recv`) → `id`, параметри ICE і DTLS, кандидати ICE |
| `connectTransport` | обидва | клієнт → сервер | параметри DTLS клієнта → – |
| `produce` | broadcast | клієнт → сервер | `kind`, `rtpParameters`, `last`, `maxBitrate` → `producerId` |
| `endStream` | broadcast | клієнт → сервер | – → – |
| `joinStream` | watch | клієнт → сервер | – → `producerIds`, можливості RTP |
| `consume` | watch | клієнт → сервер | можливості RTP клієнта, `producerId` → `consumerId`, `kind`, `rtpParameters` |
| `streamEnd` | watch | сервер → клієнт | трансляцію завершено |
| `streamerDisconnect` | watch | сервер → клієнт | з'єднання зі стрімером втрачено |
| `streamerReconnected` | watch | сервер → клієнт | новий `producerId` після повернення стрімера |

Методи відповідають етапам встановлення WebRTC-сеансу [@rfc8825; @w3c-webrtc]: для кожного напряму створюється окремий транспорт, параметри DTLS клієнт надсилає, коли mediasoup-client [@mediasoup-client] генерує подію `connect`, після чого медіадані йдуть протоколом SRTP через пару кандидатів, обрану ICE [@rfc8445; @rfc8827].

**3.2.2 Публікація трансляції.** Діаграму послідовності публікації трансляції наведено на рис. @fig:seq-broadcast. Вона деталізує крок 5 сценарію @sc:browser-broadcast, який використовує й сценарій @sc:app-broadcast.

![Діаграма послідовності публікації трансляції](../diagrams/fig-seq-broadcast.png){#fig:seq-broadcast width=16cm}

Сторінка `/broadcast` (хук `useStreamer`) створює запис трансляції запитом `POST /streams` і відкриває з'єднання `/ws/streams/:streamId/broadcast`. Обидва звернення проходять перевірку `validateWsJwt`, яка розшифровує cookie сеансу Auth.js ключем `AUTH_SECRET`, тож сервер сигналізації перевіряє сеанс без звернення до вебзастосунку. Підключення переводить трансляцію в стан `connecting`. Запит `getRtpCapabilities` створює маршрутизатор mediasoup на найменш завантаженому процесі-обробнику (worker). Далі клієнт викликає `produce` для кожної доріжки, і прапорець `last` останньої доріжки переводить трансляцію в стан `live`. Запит `endStream` фіксує завершення з причиною `streamer_stop`, а закриття сокета звільняє ресурси mediasoup.

Контекст активної трансляції (маршрутизатор, транспорти, продюсери й споживачі, таймер очікування повернення) зберігається лише в пам'яті, у реєстрі `StreamsService`; у базі даних – тільки статус і час трансляції.

**3.2.3 Перегляд трансляції.** Процес перегляду, що відповідає сценарію @sc:watch, наведено на рис. @fig:seq-watch.

![Діаграма послідовності перегляду трансляції](../diagrams/fig-seq-watch.png){#fig:seq-watch width=16cm}

Шлях `/<streamId>/watch` виключено з переадресації на сторінку входу у `proxy.ts` [@nextjs-proxy]. Відвідувачу без сеансу сторінка `Watch` виконує вхід через провайдер `guest` (ФВ-03), який повторно використовує запис гостя, збережений у `localStorage`, або створює новий з роллю `guest`, випадковим іменем та аватаром. Запит `joinStream` додає глядача до `stream_to_user` і повертає ідентифікатори продюсерів; клієнт створює приймальний транспорт, початковий бітрейт якого сервер обчислює з максимального бітрейту відео трансляції, і виконує `consume` для кожного продюсера. Подію `streamerReconnected` клієнт обробляє споживанням нового продюсера, а `streamEnd` – заміною плеєра повідомленням про завершення; подію `streamerDisconnect` сервер надсилає, але клієнт її не обробляє. Закриття сокета видаляє запис глядача зі `stream_to_user`.

**3.2.4 Вхід у настільному застосунку.** Google блокує OAuth-вхід у вбудованих вебпереглядачах [@google-embedded-webviews], тому нативним застосункам рекомендовано використовувати системний браузер і локальну адресу зворотного виклику [@rfc8252; @google-oauth-native]. Взаємодію, що реалізує ФВ-02, наведено на рис. @fig:seq-desktop-auth.

![Діаграма послідовності входу в настільному застосунку через системний браузер](../diagrams/fig-seq-desktop-auth.png){#fig:seq-desktop-auth width=16cm}

Головний процес генерує `verifier`, обчислює `challenge` = SHA-256(`verifier`) за схемою PKCE [@rfc7636], запускає HTTP-сервер на `127.0.0.1` з вільним портом і відкриває в системному браузері `/api/desktop-auth/start` з параметрами `port`, `state` і `challenge`. Вебзастосунок зберігає їх у короткочасному cookie та перенаправляє до Google. Після входу маршрут `/complete` перевіряє, що сеанс не гостьовий, видає пов'язаний з `challenge` одноразовий код (дійсний 120 с) і перенаправляє браузер на локальний сервер. Головний процес звіряє `state` і передає код і `verifier` сторінці, яка обмінює їх на сеанс через провайдер `desktop`. Перехоплений код без `verifier` непридатний, а повторне використання блокується реєстром ідентифікаторів `jti`.

**3.2.5 Слідування за застосунком.** Вимога ФВ-09 передбачає перехід трансляції на нові вікна застосунку, зокрема відкриті його дочірніми процесами, і повернення до початкового вікна. Алгоритм класу `SourceFollower` наведено на діаграмі діяльності (рис. @fig:act-follow).

![Діаграма діяльності режиму слідування за застосунком](../diagrams/fig-act-follow.png){#fig:act-follow width=14cm}

Під час вибору вікна фіксується «якір»: ідентифікатор джерела, PID, ім'я виконуваного файлу та корінь сімейства процесів (вікна процесів-оболонок якорем не стають). Кожні 1500 мс клас порівнює перелік вікон від `desktopCapturer` [@electron-desktop-capturer] з попереднім; кандидатом є вікно процесу того самого сімейства, створеного після фіксації якоря, з іншим виконуваним файлом, а з кількох обирається найновіше. Коли вікно слідування зникає, трансляція повертається до якоря; якщо зникло й воно, клас чекає до 20 с і вимикає слідування з подією `lost`. Кожне перемикання сторінка отримує як подію `stream:sourceChanged` і замінює доріжку без перестворення трансляції.

**3.2.6 Життєвий цикл трансляції.** Стани трансляції (поле `status` таблиці `stream`) і причини завершення (поле `endReason`) наведено на діаграмі станів (рис. @fig:state-stream).

![Діаграма станів трансляції](../diagrams/fig-state-stream.png){#fig:state-stream width=14cm}

Якщо сокет стрімера закривається до `endStream`, сервер надсилає глядачам `streamerDisconnect` і запускає таймер з інтервалом 6 с та обмеженням `MAX_ATTEMPTS = 5` (ФВ-16), не змінюючи статусу в базі даних. Повторне підключення стрімера за активного таймера дає стан `reconnecting`, а `produce` з прапорцем `last` – знову `live`; інакше трансляція завершується з причиною `timeout`. Під час запуску сервер завершує незавершені трансляції з причиною `server_force`, оскільки їхній контекст у пам'яті втрачено. Значення `admin_force` оголошено, але не використовується.

## 3.3 Проєктування структури бази даних

**3.3.1 Логічна модель даних.** Схему бази даних визначено в пакеті `@stream-share/db` і застосовано до PostgreSQL засобами Drizzle. Діаграму «сутність – зв'язок» у нотації IE наведено на рис. @fig:er.

![Діаграма «сутність – зв'язок» бази даних](../diagrams/fig-er.png){#fig:er width=15cm}

Таблиця `stream_to_user` реалізує зв'язок «багато до багатьох» між трансляціями та їхніми поточними глядачами. Таблиці `user` і `account` мають структуру, якої очікує адаптер Auth.js: власний `DrizzleAdapter` створює користувача під час першого входу через Google і прив'язує до нього обліковий запис провайдера. ## 3.4 Проєктування класів

**3.4.1 Класи сервера сигналізації.** Код сервера сигналізації поділено на три шари: контролери, сервіси та репозиторії. Діаграму класів наведено на рис. @fig:classes-signaling.

![Діаграма класів сервера сигналізації](../diagrams/fig-classes-signaling.png){#fig:classes-signaling width=16cm}

Контролери реєструють маршрути Fastify [@fastify-docs; @fastify-websocket]: `StreamsController` – REST-маршрути трансляцій і обидва WebSocket-канали, `UsersController` – маршрут `GET /users/:userId`. Сервіси містять бізнес-логіку: `StreamsService` – трансляції та реєстр контекстів, `StreamersService` і `ViewersService` – транспорти, продюсери й споживачі стрімера та глядачів, `UsersService` – користувачів і очищення гостей, `MediasoupService` – процеси-обробники, маршрутизатори та транспорти. Репозиторії інкапсулюють запити Drizzle. Залежності передаються через конструктори: замість DI-фреймворку клас `Container` зберігає словник «клас → екземпляр», а `DiService` (декоратор Fastify `app.di`) під час запуску створює об'єкти в порядку залежностей. Граф об'єктів явний і статично типізований.

**3.4.2 Міжпроцесна взаємодія настільного застосунку.** Сторінка настільного застосунку працює з увімкненою ізоляцією контексту [@electron-context-isolation] і не має прямого доступу до API Node.js та Electron. Шар міжпроцесної взаємодії, названий у коді «conveyor», наведено на рис. @fig:classes-conveyor.

![Діаграма класів міжпроцесної взаємодії настільного застосунку](../diagrams/fig-classes-conveyor.png){#fig:classes-conveyor width=16cm}

Абстрактний клас `ConveyorApi` обгортає `ipcRenderer`; його нащадки `AppApi`, `AuthApi`, `WindowApi` і `StreamApi` preload-скрипт публікує як `window.conveyor` через `contextBridge`. У головному процесі функції `register*Handlers` реєструють обробники через `handle()`, а події надсилаються через `sendEvent()`. Обидві сторони спираються на схеми zod `ipcInvokeSchemas` (аргументи й результат каналу) та `ipcEventSchemas` (дані подій): сторона рендерингу отримує з них типи, а головний процес перевіряє дані під час виконання. Захоплення звуку виконує утилітарний процес [@electron-utility-process], який передає дані сторінці напряму через пару портів `MessageChannelMain`.

## Висновки до розділу 3

Спроєктована система складається з вебзастосунку, сервера сигналізації з SFU-пересиланням медіапотоків і настільного застосунку-оболонки, які спираються на спільні пакети схем даних, протоколу та конфігурації. Систему розгортають як набір контейнерів Docker Compose за зворотним проксі Caddy; медіатрафік WebRTC іде напряму до сервера сигналізації через виділений діапазон портів.

Діаграми процесів формалізують публікацію й перегляд трансляції за протоколом сигналізації поверх WebSocket, вхід у настільному застосунку за схемою PKCE, слідування за вікнами застосунку та відновлення після втрати з'єднання стрімера. Модель даних з п'яти таблиць узгоджено з Auth.js і JWT-сеансами; класи сервера поділено на контролери, сервіси та репозиторії з явним впровадженням залежностей, а міжпроцесну взаємодію типізовано схемами zod. Ці рішення є основою реалізації, описаної в розділі 4.
