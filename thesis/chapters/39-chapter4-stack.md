# 4 Програмна реалізація системи

## 4.1 Вибір інструментів розробки

**4.1.1 Склад технологічного стеку.** Система поєднує вебзастосунок, сервер сигналізації та пересилання медіапотоків і настільний застосунок, тому інструменти обирали за трьома критеріями: єдина мова для всіх модулів, спільний код клієнта й сервера та підтримка WebRTC на кожній стороні. Перелік технологій з версіями з файлу блокування залежностей наведено в табл. @tbl:stack.

: Технології розробки програмної системи {#tbl:stack}

| Технологія | Версія | Призначення в системі |
|---|---|---|
| TypeScript | 6.0.3 (web), 7.0.2 (інші пакети) | мова програмування всіх модулів |
| pnpm (workspaces) | 12.3.4 | менеджер пакетів, монорепозиторій `apps/*`, `packages/*` |
| Next.js, React, Tailwind CSS | 16.2.6, 19.2.4, 4.3.0 | вебзастосунок: сторінки, API-маршрути, перевірка доступу, стилі |
| Auth.js (next-auth) | 5.0.0-beta.31 | вхід через Google, гостьові сеанси, JWT-сеанс |
| Fastify, `@fastify/websocket` | 5.8.5, 11.2.0 | REST- і WebSocket-інтерфейси сервера сигналізації |
| mediasoup, mediasoup-client | 3.20.5, 3.21.0 | сервер-посередник SFU та його клієнт у браузері |

Найвагоміші рішення – вибір сервера SFU, платформи настільного застосунку та засобу доступу до даних – обґрунтовано нижче порівнянням з альтернативами.

**4.1.2 Мова програмування та організація коду.** TypeScript розширює JavaScript строгою типізацією, що дозволяє виявляти помилки ще в редакторі коду [@typescript]. Усі модулі виконуються в середовищах JavaScript, тому протокол WebSocket, розрахунок бітрейту, схеми бази даних і перевірку конфігурації винесено в спільні пакети, які застосунки підключають через протокол `workspace:` менеджера pnpm [@pnpm-workspaces]. Бібліотека zod перевіряє дані під час виконання й виводить зі схеми статичний тип [@zod], тож схема змінних середовища водночас задає тип конфігурації та зупиняє запуск сервера за некоректних значень.

**4.1.3 Вебзастосунок і автентифікація.** Next.js – фреймворк на основі React для повностекових вебзастосунків із серверними компонентами [@nextjs-docs; @react-19]. На його API-маршрутах реалізовано передавання сеансу настільному застосунку, а у файлі Proxy, який виконується до завершення запиту й призначений для перевірки автентифікації та перенаправлень [@nextjs-proxy], – вимогу ФВ-04.

З двох стратегій сеансу Auth.js обрано JWT: сеанс зберігається в зашифрованому токені у файлі cookie з атрибутом HttpOnly, що не потребує запитів до бази даних, але не дозволяє відкликати сеанс до закінчення строку дії [@authjs-session-strategies]. Завдяки цьому сервер сигналізації сам розшифровує той самий файл cookie під час встановлення з'єднання WebSocket. Обмеження щодо відкликання прийнятне, бо функцій блокування користувачів не реалізовано.

**4.1.4 Сервер сигналізації та пересилання медіапотоків.** Fastify – вебфреймворк для Node.js із низькими накладними витратами [@fastify-docs]; плагін `@fastify/websocket` обслуговує маршрути WebSocket [@rfc6455] тим самим маршрутизатором і хуками, що й HTTP [@fastify-websocket], тому перевірку сеансу виконано однаково для обох видів маршрутів. Сервери SFU порівняно в табл. @tbl:alt-sfu.

: Порівняння серверів SFU {#tbl:alt-sfu}

| Критерій | mediasoup | Janus | LiveKit |
|---|---|---|---|
| Форма постачання | модуль Node.js, не окремий сервер [@mediasoup-design] | окремий сервер загального призначення мовою C [@janus-docs] | окремий сервер SFU, хмарний сервіс або власне розгортання [@livekit-about] |
| Взаємодія з прикладним кодом | низькорівневий API в тому самому процесі Node.js [@mediasoup-design] | повідомлення JSON через HTTP, WebSocket та інші транспорти до серверних плагінів [@janus-docs] | модель кімнат, учасників і треків через власні SDK [@livekit-about] |
| Масштабування | процеси Worker мовою C++, по одному на ядро процесора; з'єднання маршрутизаторів (`pipeToRouter`) [@mediasoup-scalability] | не зазначено | не зазначено |

Janus і LiveKit є окремими серверами з власною моделлю взаємодії, тоді як mediasoup вбудовується в прикладний процес (табл. @tbl:alt-sfu). Тому життєвий цикл трансляції, її статуси в базі даних і повторне підключення стрімера керуються з того самого коду, що обслуговує сигналізацію, а низькорівневий API дозволяє задати порядок кодеків і межі бітрейту з підрозділу 1.4. Браузерну частину реалізує mediasoup-client [@mediasoup-client]; платою за гнучкість є власний сигналізаційний протокол (табл. @tbl:ws-protocol).

**4.1.5 Настільний застосунок.** Вимоги ФВ-07–ФВ-09 потребують доступу до вікон і процесів операційної системи. Платформи Electron і Tauri порівняно в табл. @tbl:alt-desktop.

: Порівняння платформ настільного застосунку {#tbl:alt-desktop}

| Критерій | Electron | Tauri |
|---|---|---|
| Рушій відображення | Chromium у складі застосунку, однаковий для Windows, macOS і Linux [@electron-docs] | системний WebView: WebView2 (Windows), WKWebView (macOS), webkitgtk (Linux) [@tauri-webview] |
| Мова основного процесу | JavaScript у Node.js [@electron-process-model] | Rust [@tauri-architecture] |
| Розмір дистрибутиву | більший через Chromium і Node.js у складі [@electron-docs] | малий, середовище виконання не постачається [@tauri-architecture] |
| Захоплення екрана й вікон | `desktopCapturer` і обробник запитів захоплення сеансу [@electron-desktop-capturer; @electron-session] | залежить від системного WebView [@tauri-webview] |

Настільний застосунок завантажує розгорнутий вебзастосунок, і лише вбудований Chromium гарантує однакову роботу WebRTC та mediasoup-client на всіх платформах, тоді як із системним WebView вона залежала б від рушія кожної операційної системи [@tauri-webview]. Основний процес на Node.js дозволяє використати модуль electron-native-screenshare [@electron-native-screenshare] в окремому процесі UtilityProcess [@electron-utility-process; @electron-process-model]. Більший розмір дистрибутиву є прийнятною платою. Ізоляцію сторінки забезпечує ізоляція контексту, увімкнена за замовчуванням з Electron 12 [@electron-context-isolation]; інсталятори збирає electron-builder [@electron-builder].

**4.1.6 Зберігання даних.** Обрано PostgreSQL – об'єктно-реляційну СКБД з відкритим кодом, що відповідає вимогам ACID [@postgresql-about]. Для доступу до неї порівнювали Drizzle ORM і Prisma ORM. Prisma описує схему окремою декларативною мовою у файлі `schema.prisma` і потребує генерації клієнта командою `prisma generate` [@prisma-what-is]. Схеми Drizzle ORM є звичайними модулями TypeScript без кроку генерації, а запити записуються SQL-подібним або реляційним API, причому реляційний запит виконується одним SQL-запитом; міграції створює drizzle-kit [@drizzle-overview]. Обрано Drizzle ORM: його схеми безпосередньо імпортують і вебзастосунок (адаптер Auth.js), і сервер сигналізації зі спільного пакета `packages/db`.

**4.1.7 Розгортання.** Docker Compose описує в одному файлі YAML сервіси, мережі й томи [@docker-compose-model]: PostgreSQL, сервіс міграцій, сервер сигналізації з діапазоном портів RTC, вебзастосунок і зворотний проксі Caddy. Caddy автоматично отримує й поновлює сертифікати TLS [@caddy-https], що необхідно, оскільки захоплення екрана доступне лише в безпечному контексті HTTPS [@mdn-getdisplaymedia]. Образи, розгортання та інсталятори збирають робочі процеси GitHub Actions; electron-updater отримує оновлення з випусків GitHub [@electron-builder-autoupdate].
