# 4 ПРОГРАМНА РЕАЛІЗАЦІЯ СИСТЕМИ

## 4.1 Вибір інструментів розробки

Критеріями вибору інструментів розробки були єдина мова для всіх модулів, спільний код клієнта й сервера та підтримка WebRTC на кожній стороні. Склад технологічного стеку з версіями, зафіксованими у файлі блокування залежностей, наведено в табл. @tbl:stack.

: Технології розробки програмної системи {#tbl:stack}

| Технологія | Версія | Призначення в системі |
|---|---|---|
| TypeScript, pnpm (workspaces) | 6.0.3 (web), 7.0.2; 12.3.4 | мова всіх модулів; монорепозиторій із трьох застосунків і спільних модулів |
| Next.js, React, Tailwind CSS | 16.2.6, 19.2.4, 4.3.0 | вебзастосунок |
| Auth.js (next-auth) | 5.0.0-beta.31 | вхід через Google, гостьові сеанси |
| Fastify, \@fastify/websocket | 5.8.5, 11.2.0 | REST- і WebSocket-інтерфейси сервера сигналізації |
| mediasoup, mediasoup-client | 3.20.5, 3.21.0 | сервер SFU та його клієнт у браузері |
| PostgreSQL, Drizzle ORM, drizzle-kit | 16, 1.0.0-beta.22 | база даних, схеми, міграції |
| zod | 4.4.3 | перевірка конфігурації, повідомлень IPC, параметрів запитів |
| Electron, electron-native-screenshare | 35.7.5, 1.2.0 | настільний застосунок, звук окремого процесу |
| electron-vite, electron-builder, electron-updater | 5.0.0, 26.8.1, 6.8.9 | збирання, інсталятори, автоматичне оновлення |
| Docker Compose, Caddy, GitHub Actions | –, 2, – | розгортання, HTTPS, збирання й випуск |

Основною мовою обрано TypeScript, яка виявляє помилки типів до виконання програми [@typescript], а оскільки всі модулі працюють у середовищах JavaScript, протокол WebSocket, розрахунок бітрейту, схеми бази даних і конфігурацію винесено в спільні пакети робочого простору pnpm [@pnpm-workspaces]. Схеми zod перевіряють дані під час виконання й задають статичні типи [@zod].

Для вебзастосунку обрано Next.js [@nextjs-docs; @react-19], що поєднує сторінки React та API-маршрути, а його механізм Proxy перевіряє доступ до завершення запиту [@nextjs-proxy] (ФВ-04). Стратегія сеансу JWT в Auth.js зберігає сеанс у зашифрованому файлі cookie без звернень до бази даних, ціною неможливості відкликати його [@authjs-session-strategies], і цей файл cookie розшифровує й сервер сигналізації.

Сервер сигналізації та пересилання медіапотоків побудовано на Fastify: плагін \@fastify/websocket обслуговує маршрути WebSocket [@rfc6455] тими самими хуками Fastify, що й HTTP [@fastify-docs; @fastify-websocket], тому сеанс перевіряється однаково. Сервери SFU порівняно в табл. @tbl:alt-sfu.

: Порівняння серверів SFU {#tbl:alt-sfu}

| Критерій | mediasoup | Janus | LiveKit |
|---|---|---|---|
| Форма постачання | модуль Node.js [@mediasoup-design] | окремий сервер мовою C [@janus-docs] | окремий сервер або хмарний сервіс [@livekit-about] |
| Взаємодія з прикладним кодом | низькорівневий API в тому самому процесі | JSON-повідомлення до серверних плагінів | кімнати, учасники й треки через SDK |

Вбудований у процес сервера сигналізації mediasoup дозволяє керувати трансляцією та повторним підключенням стрімера з одного коду й задати порядок кодеків і межі бітрейту з підрозділу 1.4. Платою є власний сигналізаційний протокол (табл. @tbl:ws-protocol) з клієнтом mediasoup-client [@mediasoup-client].

Для настільного застосунку визначальними є вимоги ФВ-07–ФВ-09, які потребують доступу до вікон і процесів операційної системи. Electron і Tauri порівняно в табл. @tbl:alt-desktop.

: Порівняння платформ настільного застосунку {#tbl:alt-desktop}

| Критерій | Electron | Tauri |
|---|---|---|
| Рушій відображення | вбудований Chromium [@electron-docs] | системний WebView [@tauri-webview] |
| Основний процес | Node.js [@electron-process-model] | Rust [@tauri-architecture] |
| Захоплення екрана й вікон | модуль desktopCapturer [@electron-desktop-capturer; @electron-session] | залежить від WebView [@tauri-webview] |

Настільний застосунок відкриває розгорнутий вебзастосунок, і лише Chromium гарантує однакову роботу WebRTC на всіх платформах, а Node.js в основному процесі дозволяє запустити бібліотеку electron-native-screenshare [@electron-native-screenshare] в окремому службовому процесі UtilityProcess [@electron-utility-process]. Платою є більший розмір дистрибутиву [@electron-docs].

Для зберігання даних обрано PostgreSQL – об'єктно-реляційну СКБД з відкритим кодом, що відповідає вимогам ACID [@postgresql-about]. Prisma ORM описує схему окремою мовою й потребує генерації клієнта [@prisma-what-is], а схеми обраного Drizzle ORM є модулями TypeScript без такого кроку [@drizzle-overview], тому їх зі спільного модуля доступу до бази даних імпортують і адаптер Auth.js, і сервер сигналізації.

Сервіси системи розгортаються за єдиним описом Docker Compose [@docker-compose-model]; Caddy автоматично отримує сертифікати TLS [@caddy-https], а HTTPS обов'язковий для захоплення екрана [@mdn-getdisplaymedia]. Інсталятори збирає electron-builder [@electron-builder], оновлення з випусків GitHub отримує electron-updater [@electron-builder-autoupdate].
