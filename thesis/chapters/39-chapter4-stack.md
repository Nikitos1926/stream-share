# 4 ПРОГРАМНА РЕАЛІЗАЦІЯ СИСТЕМИ

## 4.1 Вибір інструментів розробки

Критеріями вибору інструментів розробки були єдина мова для всіх модулів, спільний код клієнта й сервера та підтримка WebRTC на кожній стороні. Склад технологічного стеку з версіями, зафіксованими у файлі блокування залежностей, наведено в табл. @tbl:stack.

: Технології розробки програмної системи {#tbl:stack}

| Технологія | Версія | Призначення в системі |
|---|---|---|
| TypeScript, pnpm (workspaces) | 6.0.3 (web), 7.0.2; 12.3.4 | мова всіх модулів; монорепозиторій із трьох застосунків і спільних модулів |
| Next.js, React, Tailwind CSS | 16.2.6, 19.2.4, 4.3.0 | вебзастосунок |
| Auth.js (next-auth) | 5.0.0-beta.31 | вхід через Google, гостьові сеанси |
| Fastify, \@fastify/websocket | 5.8.5, 11.2.0 | REST- і WebSocket-інтерфейси сервера сигналізації |
| mediasoup, mediasoup-client | 3.20.5, 3.21.0 | сервер SFU та його клієнт у браузері |
| PostgreSQL, Drizzle ORM, drizzle-kit | 16, 1.0.0-beta.22 | база даних, схеми, міграції |
| zod | 4.4.3 | перевірка конфігурації, повідомлень IPC, параметрів запитів |
| Electron, electron-native-screenshare | 35.7.5, 1.2.0 | настільний застосунок, звук окремого процесу |
| electron-vite, electron-builder, electron-updater | 5.0.0, 26.8.1, 6.8.9 | збирання, інсталятори, автоматичне оновлення |
| Docker Compose, Caddy, GitHub Actions | –, 2, – | розгортання, HTTPS, збирання й випуск |

Основною мовою обрано TypeScript, яка виявляє помилки типів до виконання програми. Оскільки всі модулі працюють у середовищах JavaScript, протокол WebSocket, розрахунок бітрейту, схеми бази даних і конфігурацію винесено в спільні пакети робочого простору pnpm, а схеми zod перевіряють дані під час виконання й водночас задають їхні статичні типи.

Для вебзастосунку обрано Next.js, що поєднує сторінки React та API-маршрути, а його механізм Proxy перевіряє доступ до сторінок ще до їх формування (ФВ-04). Стратегія сеансу JWT в Auth.js зберігає сеанс у зашифрованому файлі cookie без звернень до бази даних, ціною неможливості відкликати його [@authjs-session-strategies], і цей файл cookie розшифровує й сервер сигналізації.

Сервер сигналізації та пересилання медіапотоків побудовано на Fastify: плагін \@fastify/websocket обслуговує маршрути WebSocket тими самими хуками Fastify, що й HTTP-маршрути, тому сеанс перевіряється однаково. Як сервер SFU обрано mediasoup – модуль Node.js, у якому медіадані пересилають процеси-обробники мовою C++, а сигнальний протокол застосунку не нав'язується [@mediasoup-design]. Вбудований у процес сервера сигналізації mediasoup дозволяє керувати трансляцією та повторним підключенням стримера з одного коду, а його програмний інтерфейс маршрутизаторів, транспортів і споживачів дає змогу задати порядок кодеків і межі бітрейту (табл. @tbl:encoding) [@mediasoup-api]. Платою за це є власний сигналізаційний протокол (табл. @tbl:ws-protocol) з клієнтом mediasoup-client.

Для настільного застосунку визначальними є вимоги ФВ-07–ФВ-09, які потребують доступу до вікон і процесів операційної системи, тому його побудовано на платформі Electron. Її модуль desktopCapturer перелічує екрани й вікна, а сесія дозволяє відповісти на запит захоплення сторінки обраним джерелом [@electron-desktop-capturer; @electron-session]. Настільний застосунок відкриває розгорнутий вебзастосунок, тож вбудований рушій Chromium виконує той самий клієнтський код WebRTC, що й браузер, а Node.js в основному процесі дозволяє запустити бібліотеку electron-native-screenshare [@electron-native-screenshare] в окремому утилітарному процесі, призначеному для компонентів, схильних до збоїв [@electron-process-model].

Для зберігання даних обрано реляційну СКБД PostgreSQL. Схеми Drizzle ORM є звичайними модулями TypeScript, тому їх зі спільного модуля доступу до бази даних імпортують і адаптер Auth.js, і сервер сигналізації.

Сервіси системи розгортаються за єдиним описом Docker Compose, а Caddy автоматично отримує сертифікати TLS, і вебзастосунок працює через HTTPS. Інсталятори збирає electron-builder, оновлення з випусків GitHub отримує electron-updater.
